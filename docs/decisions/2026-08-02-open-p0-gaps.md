# Open P0 gaps — deliberately not built

**Status:** open, tracked
**Rule:** anything on this list is a **P0 requirement with no implementation**.
Not a nice-to-have, not a P1 deferred on purpose. Each entry says what is
missing, which requirement it belongs to, and what breaks because of it.

This file exists because the alternative is a gap living in one person's head.
Every item here was found by an audit rather than by a bug report, which means
nothing would have surfaced it on its own.

---

## AUTH-1 · Social login — C-1.3, P0

`POST /auth/social` (doc 06 §2) does not exist. Google, Apple and Facebook are
all absent.

**Apple is not optional.** App Store Review Guideline 4.8 requires Sign in with
Apple on any app offering third-party sign-in, so shipping Google without Apple
is a rejection, not a gap. Facebook still carries real weight in Egypt
(doc 02 C-1.3).

**What breaks:** nothing today — the phone-OTP path is complete and is the
primary identity mechanism in Egypt. This is a conversion cost, not an outage.

**Blocked on:** developer accounts for all three providers.

---

## AUTH-2 · Password reset — C-1.4, P0

`POST /auth/forgot-password` and `POST /auth/reset-password` (doc 06 §2) do not
exist. The `password_reset` OTP purpose is defined in the schema
(`otp_purpose` enum) and in `OtpPurpose`, and is issued by nothing.

**What breaks:** a diner who registered **with** a password and forgot it has
no recovery path in the app. Mitigated, not solved, by phone-OTP sign-in
(`/auth/request-otp`) — they can still get in, they just cannot fix the
password. A diner who registered without one is unaffected.

**Note:** doc 06 §2 specifies `202 always (no enumeration)` for
forgot-password. Whoever builds it should close AUTH-3 at the same time,
because the two are the same question asked at different doors.

## AUTH-3 · Registration reveals whether a phone has an account

`POST /auth/register` answers **409 `phone_exists`** for a verified number, and
`POST /auth/request-otp` answers **401 `invalid_credentials`** for an unknown
one. Either is an oracle: an attacker with a list of Egyptian mobile numbers
can learn which belong to SAHRA diners.

**Consistent with doc 06 §2**, which specifies both responses — this is a gap
in the specification as much as in the code, which is why it is recorded rather
than quietly "fixed" at one door.

**Why it has not been closed unilaterally:** removing it means registration and
sign-in must both answer identically for known and unknown numbers, which
changes the client flow (there is no `userId` to continue with). doc 06's own
answer for forgot-password — `202 always` — is the shape to copy, and copying
it at one door only would move the oracle rather than close it.

**Severity:** low on its own. Phone numbers are not secrets. It matters as
confirmation-of-membership, which is a privacy question rather than an access
one.

## ~~CANCEL-1~~ · BUILT 2026-08-02

`POST /owner/reservations/:id/cancel`, with a REQUIRED reason. doc 06 §4 now
carries the row, and a note explaining that its absence is why the diner-side
acknowledgement model shipped ahead of anything that could trigger it.

Proved as one journey rather than as parts: venue cancels → the table is free
again (asserted against the availability endpoint AND by re-booking the slot,
not by reading the trigger) → the diner sees it marked cancelled-by-restaurant
with the reason → acknowledges → it moves to past.

**It found a bigger bug on the way.** `ReservationsService.createHold` has
always accepted and stored a `userId`; the CONTROLLER never passed one, so
**every reservation ever created through the HTTP API had `user_id = NULL`**
and would never appear in that diner's own `GET /reservations`. The
confirmation screen hid it, because that renders the response body rather than
looking the reservation up. Fixed with an optional auth guard; guest booking
still works.

## NOTIFY-1 · There is no way to reach a diner — C-4.7, P0

Nothing in `apps/api/src` sends a notification of any kind. Confirmed by grep:
no FCM, no push, no device registry, no in-app centre.

> **CORRECTION, 2026-08-02.** An earlier version of this entry said
> notifications were blocked on company registration. **That is not true and
> was never a finding — it was an assumption, and it is recorded here as wrong
> so no future reader treats it as fact.**
>
> Firebase Cloud Messaging needs a **free Firebase project on an ordinary
> Google account**. Android push works from that today, with no company and no
> paperwork. What genuinely does require company registration is a different
> list: the **WhatsApp Business API**, an **SMS aggregator and sender ID**, and
> a **store listing under a company name**. The only external dependency in
> push itself is **iOS**, which needs an Apple Developer account for the APNs
> key — and even that may be an individual account.
>
> Nothing below Stage 2 is blocked on anything outside this repository.

**What breaks:** every one of these is P0 and none can happen —

| | requirement |
|---|---|
| "the restaurant cancelled your table" | CANCEL-1 exists now; nothing tells the diner |
| 24h and 2h reminders | C-3.9, "single biggest no-show reducer" |
| booking confirmed | doc 11 flow 3, node S |
| notification centre + per-event preferences | C-4.7 |

### Stage 1 — needs no external account. **BUILT 2026-08-02.**

1. **`devices` table + `POST /devices`.** Token scoped to a user and
   **revoked on sign-out** — a push token left attached to a signed-out user
   sends someone else's reservation to the wrong phone, which on a shared or
   resold handset is a privacy incident, not an annoyance.
2. **`notifications` table**, so a notification has a record independent of
   whether delivery succeeded. Delivery is the part that fails; the fact that
   we owed someone a message should not.
3. **Queue + send worker behind an interface**, with a logging implementation
   — the same shape as `OtpDelivery`, and with the same production guard: the
   logging adapter must **refuse to construct when `NODE_ENV=production`**, so
   it cannot ship by accident.
4. **The first real trigger, end to end:** a venue cancellation produces a
   notification record. CANCEL-1 exists, so this can be proved from its actual
   cause rather than from a synthetic event — which is the mistake the
   acknowledgement model already made once.

**What shipped:** `devices` + `notifications` tables; `POST /devices` and
`DELETE /devices` (revoked on sign-out, and `allDevices` logout revokes push
too); `PushDelivery` port with `LoggingPushDelivery`, which **refuses to
construct under `NODE_ENV=production`**; and the venue-cancellation trigger
wired end to end — a cancellation writes a notification record carrying the
venue, the reason and the venue-local time.

`notify()` never throws and runs AFTER the cancellation commits: a table that
failed to be released because a push timed out would be strictly worse than a
diner who has to open the app.

### Stage 2 — the FCM adapter. **BLOCKED ON CREDENTIALS.**

Not started, and not to be started until the credentials exist. See the
request at the end of this file.

### Current product limitation, stated plainly

**Until Stage 2 lands, a venue cancellation reaches only diners who open the
app.** The reason is that **delivery is not yet wired** — not that it cannot
be. Someone who booked last week and is driving to the restaurant will not see
it. The acknowledgement model is correct and does not imply coverage it does
not have.

## IDEM-1 · CLAUDE.md rule 2 is true of 3 mutations out of 25

**Found 2026-08-02, while wiring the bookings screens. Needs a decision.**

CLAUDE.md rule 2 and doc 06 §1 both say *"every API mutation is idempotent
(`Idempotency-Key` header)"*. The real number is **3 of 25**:

| carries a key | |
|---|---|
| `POST /reservations/holds` | |
| `POST /reservations/holds/{id}/confirm` | |
| `POST /owner/restaurants/{restaurantId}/reservations` | |

All three are the ones where a replay creates a **duplicate table booking**.
That is not a coincidence — it is where the requirement was actually felt,
which is why it is the only place it got built. Everything else — all of auth,
all of owner venue config, admin approve/reject, devices, acknowledge — has
none.

Nothing detected this, and the reason is worth recording: the only enforcement
was three hand-written `if` blocks inside three handlers, plus a check in the
Flutter `FakeTransport` that rejected any non-GET without a key. That check
agreed with the rule and passed for four weeks, because **the only mutations
any test drove were the two compliant ones**. A guard pointed exclusively at
the compliant cases is not a guard.

### What was done now

- `apps/api/src/shared/api/idempotency-contract.spec.ts` reads the committed
  spec, enumerates every mutation, and pins both lists. A twenty-sixth
  mutation without a key now fails a test and forces a decision instead of
  quietly making the doc a little more false.
- The Flutter fake stopped asserting a rule it could not observe. It validates
  the SHAPE of a key that is sent; membership is counted where all 25 are
  visible.

### DECIDED 2026-08-02 — narrow fix, not the sweep

**Product owner's decision, recorded in their words:** the three compliant
endpoints are the ones where a replay double-books a table, so the costly case
is already closed. Refresh is the remaining case that hurts a real diner — a
retry on a dropped connection currently looks like token theft and revokes the
family, signing them out mid-booking with no explanation.

**Built:** `POST /auth/refresh` is replay-safe. `TokenService.rotate`
distinguishes a retried rotation from reuse by three facts together — the
replay is inside a 60-second window, the replacement token has never been
used, and the caller presents the same IP and user agent the token was issued
to. All three, because:

- time alone disarms reuse detection for a minute (the existing theft e2e went
  red on the first cut, which is how this was caught);
- "unused replacement" alone cannot tell a thief from a lost response;
- `null === null` must not read as "same client", so grace requires POSITIVE
  evidence and an unrecorded IP does not qualify.

Four e2e tests, and the check was deliberately weakened once to watch two of
them fail.

**NOT a header.** Refresh carries no `Idempotency-Key` and stays on the list
below, because the contract test counts headers and a list that promoted it
would be describing intent again. It is idempotent by mechanism, not by
protocol — the credential a key would deduplicate on IS the request body.

**Residual risk, stated:** a thief on the same NAT with a spoofed user agent,
replaying inside 60 seconds, before the victim uses their new token, still
gets a session. Narrower than what it replaces. Closing it fully needs device
binding (doc 09 §1.1, not built).

### The 21 mutations still without idempotency

Listed so the gap is visible rather than implied. None is scheduled.

| endpoint | what a retry does today |
|---|---|
| `POST /v1/owner/restaurants` | **creates a second restaurant** |
| `POST /v1/owner/restaurants/{restaurantId}/tables` | **creates a duplicate table** |
| `POST /v1/owner/restaurants/{restaurantId}/shifts` | **creates a duplicate shift** |
| `POST /v1/auth/register` | nothing — the phone uniqueness constraint absorbs it, which is why nobody noticed |
| `POST /v1/auth/verify-otp` | burns the challenge twice; the second attempt reads as a wrong code |
| `POST /v1/auth/resend-otp` | consumes one of the three-per-ten-minutes budget |
| `POST /v1/auth/request-otp` | as above |
| `POST /v1/auth/login` | nothing — issues a second independent session |
| `POST /v1/auth/logout` | nothing — revoking twice is revoking once |
| `POST /v1/devices` | nothing — upserts on the token |
| `DELETE /v1/devices` | nothing — a delete |
| `POST /v1/reservations/{id}/acknowledge-cancellation` | nothing — conditional UPDATE, writes the timestamp once |
| `POST /v1/owner/reservations/{id}/cancel` | nothing — the status predicate makes the second call a 409, not a second cancellation |
| `POST /v1/admin/restaurants/{id}/approve` | nothing — idempotent state transition |
| `POST /v1/admin/restaurants/{id}/reject` | nothing — as above |
| `POST /v1/owner/restaurants/{id}/submit` | nothing — as above |
| `PATCH /v1/owner/restaurants/{id}` | nothing — a set, not an increment |
| `PATCH /v1/owner/restaurants/{restaurantId}/tables/{tableId}` | nothing — as above |
| `PATCH /v1/owner/restaurants/{restaurantId}/shifts/{shiftId}` | nothing — as above |
| `DELETE /v1/owner/restaurants/{restaurantId}/tables/{tableId}` | nothing — a delete |
| `DELETE /v1/owner/restaurants/{restaurantId}/shifts/{shiftId}` | nothing — a delete |

**Three of the 21 genuinely create rows on a retry** — the first three. They
are owner-facing and reached from the management app, which is not built, so
nobody can hit them yet. That is the reason they are not urgent; it is not a
reason they are safe.

## SCHEMA-1 · `neighborhood` is not bilingual — CLAUDE.md rule 5

`restaurants.neighborhood` is a single `VARCHAR(80)`, so the database holds one
spelling and it is the Latin one. **`Zamalek` appears on a fully Arabic
screen**, in the meta line of every search result and on every venue page.

CLAUDE.md rule 5 is *bilingual by column* (`name_en`/`name_ar`); this column
predates it.

**Not papered over in the client on purpose.** A hardcoded lookup of Cairo
neighbourhoods in the app would drift from whatever owners actually type, and
would be wrong for every venue outside the list.

**The fix is a migration** to `neighborhood_en` / `neighborhood_ar`, plus the
seed, `search-doc.ts`, both response DTOs, and the Flutter mapping.

## What Stage 2 needs from the product owner

Concretely, so nothing is ambiguous:

1. **A Firebase project.** Free tier, ordinary Google account. Name it
   something like `sahra-prod` — one project can serve both apps.
2. **Add an Android app** to it with package name `app.sahra.sahra_customer_app`
   (from `apps/customer_app/android/app/build.gradle.kts`). This produces
   `google-services.json`, which goes at
   `apps/customer_app/android/app/google-services.json`.
3. **A service-account key** — Firebase console → Project settings → Service
   accounts → *Generate new private key*. A JSON file.

**WHERE THE SERVICE-ACCOUNT KEY GOES, AND WHAT IT MUST NEVER BE COMMITTED AS:**

- It is a **server credential that can send push to every SAHRA user**. Treat
  it exactly like `JWT_ACCESS_SECRET`.
- **Never in git.** `.gitignore` already excludes `google-services.json` and
  `*.pem`/`*.key`; the service-account JSON must be added to that list before
  the file is downloaded, not after — a secret committed once is a secret
  rotated, even if the commit is reverted.
- Locally: a path in `.env` (`FIREBASE_SERVICE_ACCOUNT=/absolute/path.json`),
  with `.env` already gitignored.
- Deployed: the JSON **contents** in a secrets manager (ECS task secret /
  Parameter Store), injected as an env var. Not a file baked into an image.
- `google-services.json` on the Android side is **not** a secret in the same
  sense (it ships inside the APK), but it is still gitignored today and that
  should stay — it identifies the project and there is no reason to publish it.

**Tell me when the project and the key exist and I will build the adapter.**
Until then Stage 1 runs against the logging implementation, which refuses to
construct in production.
