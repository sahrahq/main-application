# NOTIFY-1 Stage 2 — push, and the iOS gap made impossible to miss

**Date:** 2026-08-10
**Project:** `sahra-4881d`, Analytics off, **Android app only.**
**Handover status:** `2026-08-09-firebase-handover.md`.

---

## 1. The seam held

`notifications.module.ts` said the FCM swap would be one binding and nothing
above `PushDelivery` would change. It was, and nothing did — no service, no
controller, no test of the read half was touched to make push work. That claim
is now checked rather than asserted.

What did change is everything the claim did **not** cover, and it turned out to
be most of the work: the credential loader, platform readiness, a health
endpoint, dead-token handling, and the entire client half.

## 2. Three things were checked before anything was wired

Because the product owner asked for them first, and two of the three were wrong.

### 2.1 The gitignore had three holes

`git check-ignore` on nine candidate paths, rather than reading the patterns:

| | before |
|---|---|
| `apps/api/.env` | ignored |
| `google-services.json`, anywhere | ignored |
| `GoogleService-Info.plist` | ignored |
| **`*.p8`** (APNs key) | **NOT ignored** |
| **`secrets/…`** | **NOT ignored** |
| **`sahra-4881d-firebase-adminsdk-….json`** | **NOT ignored** |

All three were added before any credential was placed. The previous handover
doc had claimed the `.p8` was "already ignored by the `*.pem` / `*.key` rules",
which is not how glob patterns work — a `.p8` is neither.

**Reading the patterns is not checking.** `git check-ignore -q <path>` is the
only authority, and it is now what the doc reports.

### 2.2 The env var wanted a path, not the JSON

Changed from `FIREBASE_SERVICE_ACCOUNT_JSON` (inline) to
`FIREBASE_SERVICE_ACCOUNT_FILE` (absolute path). Free, because nothing had read
it yet — the variable had been declared in `.env.example` since Stage 1 and
never used.

The reason the original was wrong: **dotenv loads every `.env` value into
`process.env`**, so one `console.log(process.env)` prints the private key, and a
file a human edits by hand is a file that ends up in a diff or a screenshot.
A path is a boring string. The cost — production must mount a file — is the same
shape as `GOOGLE_APPLICATION_CREDENTIALS` and is accepted.

### 2.3 The key cannot reach a log, and that is a test

`JSON.parse` quotes a window of its input back at you when the failure is an
unexpected token:

```
JSON.parse('{"private_key": SUPERSECRETXYZ}')
→ Unexpected token 'S', ..."ate_key": SUPERSECRE"... is not valid JSON
```

Ten characters of a private key, in whatever log the boot error lands in.
`firebase.config.ts` discards the parser's message rather than chaining it, and
`firebase.config.spec.ts` feeds it five malformed files containing a
recognisable fake key and asserts no part of it appears in `message`, `stack`,
`String(err)` or a `JSON.stringify` of the error.

**And the first draft of that claim was too broad.** It said every malformation
leaks. Truncation does not — it gives `Unterminated string in JSON at position
126`. Probing the shapes found which two actually leak, and the guard-the-guard
test now uses one of those, because a hazard demonstration that does not
demonstrate the hazard is worse than none.

## 3. The google-services.json was in the wrong place, and the app id did not match

Both blocking, neither reported by anything until a Gradle build would have
failed.

- **Placed at `apps/google-services.json`.** Gradle reads
  `android/app/google-services.json`. Moved.
- **`applicationId` was `app.sahra.sahra_customer_app`** — the Flutter scaffold
  default, TODO still beside it — and the Firebase Android app is registered as
  `app.sahra.customer`. The Google Services plugin fails the build on a
  mismatch: *"No matching client found for package name"*.

Changed the app, not Firebase. **An applicationId can never change once an app
is on the Play Store** — it is the store identity, and a new one is a new
listing with no reviews and no installs. Nothing is published, so this was the
last free moment. `namespace` stays as it was: it is the R-class package, it
must match the Kotlin source directory, and it is invisible to Firebase, the
store and users.

## 4. "Push works" must not be able to look true

This is the whole design, and it exists because of one property of FCM:

> **FCM accepts an iOS send with no APNs key.** It answers with a message id.
> The failure to reach Apple happens afterwards, inside Google, and is never
> reported on the call that sent it.

So the naive implementation — forward everything — would return success for
every iPhone, set `sent_at`, leave `delivery_error` null, and record a delivery
that did not happen. And it would pass a manual test, because the tester's
Android phone rings.

There would be no signal anywhere. Four things now make that impossible:

1. **Refused before the network.** `FcmPushDelivery` checks the platform first
   and throws `ios_not_configured`. Nothing is handed to FCM, so nothing can
   succeed.
2. **Recorded.** The throw reaches `NotificationsService`, which writes the
   reason into `notifications.delivery_error` and leaves `sent_at` null. The
   database never claims an iPhone was reached.
3. **`GET /health` answers 503** and names iOS. Not a field in a 200 body — a
   degraded state inside a successful response is one nobody notices, because
   every uptime check looks at the status code.
4. **The boot log says it twice**: a banner when the module graph is built, and
   one line immediately under `SAHRA API on :3000`, which is the line a human
   actually reads.

`FIREBASE_IOS_CONFIGURED=1` turns iOS on with no code change, asserted in
`fcm-push.delivery.spec.ts`. **The flag is manual because FCM offers no way to
ask whether an APNs key exists** — inferring it from a send failure means
discovering it from a diner's missed booking.

### 4.1 `/health` had been 404 for weeks

`main.ts` has excluded `health` from the `/v1` prefix since the first commit and
no controller ever existed behind it. Nothing failed, because nothing asked. A
small instance of the same lesson, found while looking for somewhere to put the
alarm.

It is deliberately **not** wired to a container liveness probe, and doc 10's
pipeline does not do that — it runs a synthetic booking probe. A load balancer
that killed the process for having no APNs key would trade a missing iPhone
notification for a total outage.

## 5. Binding the adapter delivered nothing, and the caveat could not go yet

The agreement was to delete the in-app *"We can't alert your phone yet"* notice
in the commit that bound the adapter. **Binding it was not enough.**

Push reaches a handset only after that handset registers a token.
`POST /devices` and `DELETE /devices` shipped on 2026-08-02, were fully tested,
and **had never been called by anything** — there was no token to send. Deleting
the notice at that point would have replaced a true statement with a false one.

So the client half was built in the same batch: `firebase_messaging` behind a
`PushTokenSource` port, token registration, and `DELETE /devices` on sign-out —
which the server has required since Stage 1 and which nothing had ever done. A
token left on a signed-out account sends that person's next reservation
notification to whoever is holding the handset.

Then the notice went.

## 6. The permission is asked in exactly one place, and a counter proves it

**After a diner confirms their first booking**, and nowhere else. doc 11 §1:
asked with context, never on cold open.

This matters more than the location prompt, and the difference is worth naming:
**a location refusal can be asked again later; a notification refusal cannot.**
The OS shows that dialog once. Asking at the wrong moment does not cost one
prompt — it costs that diner push, permanently.

So it is the counter shape again: `FakePushTokenSource` counts every `request()`
and `push_test.dart` drives **every screen in the registry** and requires zero,
enumerated from the registry rather than from a list beside the test. The one
screen that does ask is asserted to ask exactly once, and not again on a second
booking in the same run.

Verified RED by making the notification centre ask: every notification screen
failed.

## 7. A dead token is revoked, not retried forever

FCM answers `registration-token-not-registered` for a reinstalled app, a wiped
phone, or a handset sold on. `devices.revoked_at` has existed since Stage 1 for
exactly this; the adapter now sets it. Without that the same dead token is
pushed to on every notification for the life of the account, and every send
reports a failure no retry can fix.

A **transient** failure does not revoke, and the distinction is the point:
revoking on a network blip would silently unsubscribe a working handset and
nothing would ever tell the diner.

The FCM error object is never rethrown — it can carry the request, and the
request contains the device token. Rethrown by code, so a registration token
does not end up in the log line that records the failure.

## 8. And one guard widened

`response-contract.spec.ts` required every `@ApiOkResponse` handler to declare
`Promise<…>`. `HealthController.check` is the first **synchronous** handler in
the codebase — it reads an injected value and returns — and was reported as
unenforced while being fully annotated.

The rule was never about promises; it is "the compiler must be checking the
shape this decorator advertises". Widened to accept any real annotation and
still refuse `any`, `unknown` and `void`. Making a synchronous function async to
satisfy a test would have been the test writing the code, and that file's own
comment says a guard that cries wolf is a guard somebody deletes.
